### Bugs found closing out the WebSocket chat gap
- **SSO/SCIM-issued tokens were still HS256** (`services/auth/src/federation/federation.module.ts` had its own standalone `JwtModule.register({ secret: ... })`, independent of `KeyManagementService`'s RS256 keypair) — every federated login would have handed the caller a token silently rejected by every other service's JWKS verification. Never exercised because nothing had driven the SSO login path in this migration. Fixed by reusing the same RS256 keypair every other issuer/verifier already agrees on.
- **`services/comms`'s chat gateway was also still on HS256** (`chat.gateway.ts` verified against a plain `JWT_SECRET`) — missed by the platform-wide RS256 migration for the same reason git-host was: that pass only covered the 14 services' `jwt.strategy.ts` REST guards, not this one hand-rolled socket handshake. Fixed with a `jwks-rsa` client mirroring the REST guard.
- **Async JWKS verification raced against the client's first message** — once the gateway's `handleConnection` verified the token via a real JWKS network fetch instead of a synchronous local-secret check, a client that emits `join` immediately after `connect` (every real client does) could reach `handleJoin` before `socket.data` was populated, always failing the membership check with a false "not a member" error. Root cause: verifying inside `handleConnection` doesn't block message delivery — Socket.IO's own `io.use()` handshake middleware does, since it runs to completion before `connect` fires on the client at all. Fixed by moving verification into `afterInit`'s `server.use(...)` middleware. Caught only because this pass live-tested an actual socket round-trip with a real client, not a curl-only or compile-only check.

### Bugs building this UI caught in already-"done" backend code

Building the git-host screens required actually driving git-host end to
end (clone → commit → push → open a PR) for the first time since it was
built — and found three real, production-breaking bugs that every prior
compile-only or curl-based check had missed:
- **git-host was still verifying the old shared HS256 secret** — missed
  entirely during the RS256/JWKS migration pass (that pass only covered
  the 14 NestJS verify-only services, not this Go one). It was silently
  rejecting every real token `auth`-service has issued since that
  migration shipped. Fixed with a Go JWKS client (`keyfunc`), same
  fetch-and-cache-the-issuer's-public-key pattern as the NestJS side.
- **`git push` unconditionally 403'd** — `git http-backend` refuses
  `receive-pack` unless `http.receivepack=true` is set per-repo;
  `GIT_HTTP_EXPORT_ALL` (already set) only covers reads. Nothing had ever
  actually pushed to a repo created by this service before. Fixed in
  `repos.Create`.
- **No CORS headers at all** — every NestJS service calls
  `app.enableCors()`; this Go service had no equivalent and none had been
  added. `curl` doesn't enforce CORS so this was invisible to every prior
  test; a real browser would have silently blocked every request. Fixed
  with a CORS-wrapping middleware around the whole mux (also handles
  preflight `OPTIONS` before it would otherwise 401 in the auth guard).
- Also added: `GET /api/repos` (list) didn't exist at all — only create
  did — so there was no way to enumerate a tenant's repos, which blocked
  the repos list screen from having anything to show.

### Bug found live-testing canary/blue-green: every real pipeline run had always failed to clone
`services/cicd`'s runner embedded the caller's JWT as HTTP Basic auth via
URL userinfo (`http://x:TOKEN@git-host/...`) when cloning a repo to run a
pipeline — but git-host's auth middleware strictly requires an
`Authorization: Bearer ...` header and rejects anything else, including
the `Authorization: Basic ...` header git's http transport actually sends
for userinfo-embedded credentials. This meant **every pipeline run that
reached the clone step had always failed**, silently, since nothing had
ever wired a real repo + real git-host + a real triggered run together in
one live test before this pass (prior environments/deployments
verification used a pipeline run without needing it to actually clone).
Fixed by passing the token via `-c http.extraHeader` instead — the same
mechanism used throughout this session's manual git testing. Verified by
triggering a real run against a real repo end to end: clone succeeded,
`docker run` executed, step logs captured, run marked `succeeded`.

## Correctness note: the RLS role split

Every tenant-scoped table across every service has `FORCE ROW LEVEL
SECURITY`, and every service's runtime pool connects as `eos_app` — a
genuinely non-superuser, non-owner Postgres role (see
`infra/docker/postgres-init/01-roles-and-databases.sql`). This matters more
than it looks: Postgres exempts superusers from RLS *regardless* of FORCE,
and the `POSTGRES_USER` in the default Postgres Docker image is a
superuser. A service connecting as that user would have RLS policies that
compile, look correct, and enforce nothing. Any new service must connect its
runtime pool as `eos_app`, never as `eos` — `eos` is for migrations only.
This has now been confirmed against real Postgres (`rolsuper=f`), not just
written and assumed correct.

Four pre-auth lookups (SCIM token, API key, OIDC login, public status page)
resolve their tenant *from* a credential the caller presents before any
`app.tenant_id` can be set — a plain `SELECT` there would return zero rows
under FORCE RLS. Each goes through a narrow `SECURITY DEFINER` SQL function
instead (see identity-federation's and api-platform's migrations for the
pattern) that returns only the columns needed for that one auth step. Any
new pre-auth lookup should follow the same shape rather than reaching for a
raw query or, worse, disabling FORCE.
